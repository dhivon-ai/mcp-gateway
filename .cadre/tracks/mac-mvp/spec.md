# Specification: macOS enterprise MCP Gateway MVP

- Track: `mac-mvp`
- Type: `feature`
- Revision: 1
- Status: proposed

## Goal and scope

Deliver a complete usable self-hosted MVP: a central Rust service and administrator website, an Apple Silicon macOS Rust CLI serving a local user website, and one agent-facing STDIO MCP gateway aggregating permitted local and remote tools. Both websites use React, strict TypeScript, and shadcn/ui.

The user has explicitly selected: complete MVP; Apple Silicon only; username/password initially; online configuration refresh; server-authoritative per-user enable/disable state; an encrypted timestamped local configuration file usable for at most one hour after successful synchronization; no offline configuration changes; remote unauthenticated, bearer-token, and OAuth authentication; centrally encrypted per-user key/value secrets with a secret-key selector when enabling bearer-token MCPs. Ordinary configuration in the central database does not require application-level encryption.

Include the complete development, test, packaging, deployment, and operator/user documentation needed to run this journey. Proposed implementation defaults below are part of the combined specification/plan approval.

Exclude hosted multi-enterprise SaaS, SAML, Intel macOS/Windows/Linux endpoint releases, legacy HTTP+SSE, universal provider-specific OAuth adapters, billing, automatic modification of existing agent configurations, and full forwarding of non-tool MCP features. Signing/notarization and public release publication are follow-up release work; the MVP provides a usable arm64 archive with checksums and documented installation.

## Functional Requirements

- FR-001: Provide a self-hosted Rust/Axum service backed by PostgreSQL migrations, serving the compiled React/TypeScript/shadcn admin website. Bootstrap the first administrator through an explicit operator command with no default password; administer ordinary users, groups, membership, account disablement, and password reset without exposing password material.
- FR-002: Authenticate administrators and users with username/password, salted Argon2id hashes, revocable opaque sessions, login throttling, and explicit roles. Proposed session maximum is 12 hours, with no automatic extension from polling. Known session/account rejection immediately invalidates endpoint authorization; a network outage may use only the still-valid previously issued lease. Password reset/account disablement invalidates affected sessions.
- FR-003: Administrators define catalog entries with stable IDs, names/descriptions, local executable/argument/environment/working-directory configuration or remote Streamable HTTP endpoint, optional structured installation command, auth mode, and tool policy. Reject invalid combinations; credential-bearing authentication fields accept scoped references/registration metadata rather than inline bearer or OAuth tokens. Remote auth modes are none, bearer, or OAuth; bearer mode requires a user-secret selection, while OAuth records supported public-client registration/scopes rather than an inline token.
- FR-004: Administrators assign catalog entries to users, groups, or all users. Grants are additive; no grant means no access. A new catalog entry grants nothing and enables nothing. Removal of the last effective grant clears the user's enablement for that MCP; reassignment requires a new enable action. Deletion or disabling a catalog entry removes its effective tools and credential bindings from subsequent snapshots.
- FR-005: Support MCP-wide tool allowlist and denylist modes based on original upstream tool names. Allowlist mode permits only listed tools, including denying new names until selected; denylist mode permits all discovered names except listed names. An empty initial allowlist exposes no tools. Admin tool policies remain authoritative over all user enablement.
- FR-006: Persist per-user MCP enablement and bearer-secret bindings centrally. Enable/disable and binding updates require an authenticated online request, current assignment, and revision-based concurrency control. A conflict returns the current state for explicit user reconsideration; do not blindly overwrite it. Changes on another client arrive through configuration refresh. Report server-confirmed enablement separately from endpoint installation/auth/availability.
- FR-007: Serve an authenticated effective configuration snapshot containing deployment/user identity, revision, catalog/runtime settings, effective tool policies, user enablement/bindings, server validation time, and expiry no later than 3,600 seconds after that validation. Only a complete validated snapshot, durably installed locally, renews freshness. A TCP connection, generic heartbeat, failed/partial response, or credential refresh cannot renew it.
- FR-008: Every running local management or gateway process attempts configuration refresh at startup and every 60 seconds, including unchanged configurations. Apply a newer validated snapshot atomically and never regress its revision. On reconnection attempt refresh immediately; requests have a proposed 10-second deadline. Under a responsive service, updated policy is observed by the next scheduled poll plus its request deadline. Outages never extend expiry, and a rejected identity/session invalidates immediately rather than entering offline mode.
- FR-009: While disconnected, tool discovery/invocation may use the last valid encrypted cache only while its lease and required credentials remain valid. At now >= expiresAt, fail closed: advertise no usable tools, reject new calls, request cancellation of running calls, and close affected upstreams. Cancellation is best effort and cannot undo an upstream side effect. Never replay side-effecting calls after reconnect.
- FR-010: Reject all user configuration mutations offline, even during the valid one-hour window: no queued enable/disable, secret/binding edits, installation, or new OAuth connections. Explain read-only/offline state in the local UI and enforce it in local APIs and CLI handlers. Logout may always clear local credentials/cache for security; deferred configuration writes are not allowed.
- FR-011: Encrypt the local configuration file with authenticated encryption (proposed AES-256-GCM), storing its key in macOS Keychain. Bind identity, deployment, schema, revision, validation time, and expiry to the protected payload; use unique nonces, user-only permissions, atomic writes, and an application-specific Application Support directory. Reject modified/corrupt ciphertext, copied configuration for another principal/deployment, missing keys, and detected clock rollback. Track elapsed time with a sleep-aware monotonic clock during execution; restart must not reset freshness. Where freshness cannot be established safely, require a new online sync.
- FR-012: Provide a per-user central key/value secret store: create, list key metadata, replace value, rename key, and delete. Values are write-only in browser CRUD APIs and never shown in normal list/read responses. Encrypt values with authenticated encryption and a server key held outside PostgreSQL; bind owner, secret ID, and version as associated data. Users cannot read/select another user's secret; ordinary admin catalog permissions do not grant secret-value access. Reject deletion of a secret referenced by enabled MCPs until those bindings are removed.
- FR-013: For bearer mode, the local UI lists only the current user's secret keys. Enabling requires choosing an owned key and binds its stable ID centrally. Resolve only credentials for currently assigned, enabled MCPs through an authenticated endpoint credential API over TLS. Keep downloaded tokens in Keychain, scoped to user/deployment/MCP/binding version, and enforce the policy lease before using them. Secret replacement becomes effective on subsequent successful refresh; deletion/revocation removes local authorization when learned, with the explicitly bounded offline window applying during outages.
- FR-014: For OAuth mode, perform interactive authorization through the local browser management flow, separate from agent-facing STDIO. Implement the selected stable MCP HTTP authorization profile: protected-resource and authorization-server discovery, authorization-code flow with PKCE S256, state/issuer/callback validation, resource-bound requests, refresh and reauthorization. Initially support administrator-supplied pre-registered public client IDs; provider-specific grant types and metadata-document hosting are outside this MVP. Reject unsupported provider requirements with actionable errors.
- FR-015: Persist OAuth access/refresh tokens and registration context encrypted centrally in managed credential records scoped to user, MCP, and the relevant native-client registration/installation. Keep endpoint copies in Keychain; do not expose them as editable generic key/value entries. Serialize refresh for a credential record and version rotated tokens atomically; cancellation/failure never overwrites a working credential with a partial result. An offline endpoint may use only its valid existing access token and lease; reconnect/refresh/reconsent requires the control plane. Central login tokens are never forwarded to upstream MCPs, and upstream tokens are never sent to unrelated origins or redirect targets.
- FR-016: Provide proposed CLI entry points: `mcp-gateway ui --server <url>` for local management/login, `mcp-gateway mcp` for agent STDIO execution using the selected deployment/account, `mcp-gateway status` for redacted status, and `mcp-gateway logout` for local cleanup and online session revocation when reachable. Preserve one configuration/cache identity per deployment/account and do not leak state across login changes. No fresh cache means no offline first login.
- FR-017: Serve compiled local UI assets from Rust on loopback, with authenticated local APIs, exact allowed Host/Origin checks, CSRF protection for mutations, and session-safe browser opening. Do not place tokens/passwords/local session capabilities in query strings, browser storage, or public logs. OAuth's narrowly validated callback is distinct from the protected management API.
- FR-018: Execute optional administrator-defined installation commands only after explicit user action while online and assigned. Use executable plus argument arrays, bounded execution, explicit working directory/environment, and user privileges. Show progress/redacted outcome; installation failure does not enable the MCP. If access expires/revokes during installation, stop owned work where possible and never commit enablement. A command succeeding locally followed by a server-write failure remains installed but disabled; retry must not silently rerun installation. Never install during catalog browsing or agent startup.
- FR-019: Aggregate supported tools from local STDIO child processes and remote Streamable HTTP servers into a single STDIO MCP interface. Use the official Rust rmcp SDK with pinned features/releases, preserve original tool schemas/results, and use deterministic namespaced agent-visible names with a collision-free route map. Preserve identity across refresh while original MCP/tool IDs are stable. Support MCP 2025-11-25 as the initial compatibility baseline; newer negotiation may be added only with explicit tests and accurate advertised capabilities.
- FR-020: Apply identity, fresh-cache validity, assignment, current central enablement, auth readiness, and tool policy to both listing and dispatch. Load the latest committed endpoint snapshot before authorizing new calls so a same-Mac confirmed change affects subsequent requests. Handle tool pagination/list updates and advertise supported tool-list changes. Requests for hidden, unknown, disabled, or expired tools are rejected without reaching the upstream. Unimplemented resources/prompts/sampling or other capabilities are not advertised or transparently forwarded.
- FR-021: Bound installation (proposed 300 seconds), upstream startup (30 seconds), network sync (10 seconds), tool calls (60 seconds), concurrency (16 in-flight tool calls), and owned shutdown (5 seconds before termination), with tested configuration controls where appropriate. Isolate upstream failures; cancel/clean up owned processes and connections on exit, expiry, disablement, and known authorization revocation. Keep stdout exclusively MCP traffic in STDIO mode.
- FR-022: Deliver admin screens for user/group management, catalog definitions, assignments, and allowlist/denylist editing, with validated forms and clear effective-access explanations. Assigned online gateways may report bounded discovered tool-name inventory without credentials or results; treat observations as untrusted metadata, never access grants. Administrators select original names from this inventory or enter names manually before discovery. Ordinary users cannot access admin APIs, and endpoint credentials/commands are never executed centrally merely to render this website.
- FR-023: Deliver local screens for login, assigned catalog, installation progress, enable/disable, bearer key selection, per-user secret management, OAuth connect/reconnect/disconnect, and redacted connection/config freshness status. Show offline read-only state and expiry; allow new server-confirmed settings only after successful validation. Distinguish missing executable, install failure, OAuth-required, expired token, offline service, and blocked tool states.
- FR-024: Deliver a self-hosted container/Compose deployment with PostgreSQL, migrations, health checks, configurable HTTPS termination, and separately supplied encryption keys; an Apple Silicon CLI archive with embedded UI assets/checksum; bootstrap/admin/user/agent guides; fixture MCP/OAuth services; and verified development/CI commands. Declare the actual minimum validated macOS version, protocol/agent compatibility, and supported browser matrix in release documentation, based on evidence rather than untested platform claims.

## Non-Functional Requirements

- NFR-001: Default deny is identical in discovery and invocation. Table-driven and integration tests cover every effective-access axis and direct-call bypass; no denied invocation reaches a fixture upstream.
- NFR-002: Enforce a hard maximum 3,600-second configuration lease independent of poll retries, token refresh, restart, sleep/wake, and cached file copying. Deterministic clock tests cover 3,599 seconds, exactly 3,600, and later; endpoint clock uncertainty or integrity failures cannot extend the lease. Trust the OS/Keychain boundary; this software does not claim resistance to a privileged attacker replacing the executable or compromising the operating system.
- NFR-003: HTTPS with certificate validation protects production control-plane and remote traffic; isolated HTTP fixture endpoints are permitted in tests only. Password/token/secret values never occur in captured logs, normal browser read APIs, plaintext configuration files, or PostgreSQL secret columns. AEAD tampering and owner/version substitution tests must fail closed. Ordinary central configuration may remain plaintext as requested.
- NFR-004: All configuration writes are online, authenticated, revision-checked, and atomic. Concurrent clients cannot resurrect revoked grants or overwrite newer state silently; restart and service recovery preserve user enablement and secret bindings.
- NFR-005: UI flows support keyboard use, accessible labels/focus/error feedback, and explicit loading/empty/error/success states. Use shared semantic shadcn tokens/components with strict TypeScript; browser interaction tests exercise the principal journeys.
- NFR-006: Rust formatting/Clippy/tests/build and frontend formatting/lint/typecheck/tests/build pass. CI includes Apple Silicon-compatible endpoint build/test coverage; Linux/container verification applies to the central service. Test fixtures cannot stand in for actual Keychain and macOS process verification.
- NFR-007: Emit redacted structured events for management changes, sync outcomes, credential/auth outcomes, and tool allow/deny/failure, with correlation IDs/duration. Do not persist MCP payloads or credential values; retention/enterprise audit exports are later scope.
- NFR-008: Prevent partial cache/vault updates through transactional/atomic persistence and tested migrations/backup restore. One upstream failure leaves other authorized tools operational, and shutdown does not leave owned child processes running.

## Acceptance Criteria

- AC-001: From the documented self-hosted deployment, bootstrap an administrator, create two users/groups, and demonstrate that a newly defined MCP is inaccessible until explicitly assigned and enabled. Ordinary-user attempts to change admin resources return authorization errors. Covers FR-001 to FR-006.
- AC-002: Exercise user, group, and all-users grants, last-grant removal, reassignment, allowlist/denylist changes, discovered/manual tool-name selection, newly discovered tool names, and direct-call attempts. Inventory reporting cannot grant access or include credentials/results. Effective listings and dispatch match the policy matrix; re-granting does not auto-enable. Covers FR-004, FR-005, FR-020, FR-022 and NFR-001.
- AC-003: Authenticate through the Mac CLI's local React UI, load identity-bound config, logout/re-login as another user/deployment, and prove no cache, Keychain token, enablement, or secret selection leaks between identities. Session rejection invalidates immediately. Covers FR-002, FR-011, FR-016, FR-017.
- AC-004: Complete successful install/enable/disable flows; check central persistence and another client refresh. Failed install, failed server commit, stale revision, and lost connectivity never display a false enabled success. Every offline mutation attempt is rejected and no mutation queue exists. Covers FR-006, FR-010, FR-018.
- AC-005: With a fake clock, use cached config at 3,599 seconds during a control-plane outage; at exactly 3,600 reject listing/calls and request upstream cleanup. Failed polls, unchanged-file rewrites, token refreshes, clock rollback, process restart, and sleep/wake do not renew it. After a successful complete authenticated refresh, recovery uses the new deadline. Covers FR-007 to FR-011 and NFR-002.
- AC-006: Refresh while online at startup/every 60 seconds; observe admin changes within the scheduled poll plus the 10-second request deadline against a responsive fixture. A confirmed same-Mac change blocks subsequent dispatch; other endpoints follow the documented polling/offline bounds. Covers FR-008, FR-020.
- AC-007: Inspect local config ciphertext and protected timestamps, verify Keychain key/token use on an actual Apple Silicon Mac, and reject altered ciphertext/missing key/copied identity/invalid expiry. Keep only ordinary config plaintext centrally. Covers FR-011 and NFR-003.
- AC-008: Add/replace/rename/delete user secrets, inspect server encryption at rest and key separation, reject cross-user reads/bindings, and choose an owned key when enabling a bearer MCP. Test missing/deleted/replaced keys and verify Authorization headers reach only the intended endpoint without leaking values into browser read responses or logs. Covers FR-012, FR-013, FR-015.
- AC-009: Against controlled OAuth and protected MCP fixtures, complete discovery/PKCE/callback validation, persist encrypted credentials centrally, call a protected tool, refresh a rotated token, and reauthorize after expiry/revocation. Test mismatched state/issuer/resource, failed/canceled flows, concurrent refresh, unsupported provider settings, and attempted unrelated-origin forwarding. Covers FR-014, FR-015.
- AC-010: Configure a standard MCP client/agent with only `mcp-gateway mcp`; discover and invoke tools from a local STDIO server and none/bearer/OAuth remote fixtures. Cover duplicate tool names, pagination/schema changes, timeouts/cancellation, malformed responses, process exit, capability accuracy, and protocol-only stdout. Covers FR-019 to FR-021.
- AC-011: Exercise both compiled websites in a browser: admin assignments/tool restrictions; user login/catalog/install/enable/secrets/OAuth; offline/read-only and expired states; denied admin access; keyboard navigation and actionable errors. Covers FR-017, FR-022, FR-023 and NFR-005.
- AC-012: Verify migrations, data durability through restart, database backup/restore including recoverable encrypted secrets with separately protected keys, and server health checks. Produce/check the arm64 archive, run it with embedded assets, and execute the complete documented deployment-to-agent manual journey. Record actual platform/protocol/browser compatibility. Covers FR-024 and NFR-006 to NFR-008.

## Additional Information

- User-directed clarification makes server enablement authoritative, replacing a local-only interpretation of the setup's enablement wording. Endpoint installation/runtime state remains local. It also adds encrypted central per-user secrets and OAuth to initial remote authentication scope. SAML remains deferred.
- Proposed stack follows the approved project: Rust/Tokio/Axum/rmcp/SQLx/PostgreSQL, React/TypeScript/shadcn/ui/Vite/Tailwind, pnpm, RustCrypto AEAD, and a maintained macOS Keychain integration. Pin compatible stable dependencies and declared platform/MSRV values in foundation work; do not copy SDK examples with obsolete dependency versions.
- The local timestamped encrypted file is a bounded authorization snapshot, not a perpetual offline identity. A still-valid policy lease does not extend an upstream token's expiry or authorize an offline edit. Provider/central session expiry can shorten usable access.
- OAuth fixture coverage proves the supported standards profile. Real providers requiring additional registration/grant policies are not silently claimed as compatible. Pre-registration of a public client ID is an explicit operator setup requirement.
- Server master encryption keys and Mac Keychain keys have separate ownership. Record versioned encryption formats and key-rotation/restore procedures; operators must retain the matching server key outside database backups. No server configuration encryption is imposed beyond secret material.
- Central and endpoint contracts carry schema/revision identity. Default session/poll/resource bounds and the proposed CLI command names are explicit approval choices. Minimum validated macOS/browser/agent versions will be recorded from the release verification, not invented in this planning operation.
- No external production credentials, OAuth providers, signing certificates, publication, or real user-data migration are required to implement fixture-backed MVP behavior. Real coding-agent/provider verification may require the user's installed client or pre-registered provider.
- References: [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [Rust SDK OAuth guide](https://github.com/modelcontextprotocol/rust-sdk/blob/main/docs/OAUTH_SUPPORT.md), [Rust SDK](https://github.com/modelcontextprotocol/rust-sdk), [RustCrypto AES-GCM](https://docs.rs/aes-gcm/latest/aes_gcm/), and the approved project artifacts under `.cadre/`. Verify exact protocol/SDK behavior against pinned releases during implementation.
