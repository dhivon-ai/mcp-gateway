# BUG-005: User management needs email, password and name

- Status: Resolved — implementation and release verification complete; final Cadre review/completion approval remains separate.
- Reported by: Product owner, 2026-10-15.
- Priority: P2.
- Source: “in user management it needs to be email, password and name.... log that as a bug”

## Reported behavior (before the fix)

Administrator user creation provides Username and Password, alongside Role.
There are no separate Email or Name fields. The public user contract contains
`username`, and user edits only support role/active state.

Evidence at reviewed product commit `52c288b`:
- `apps/web/src/admin/identities.tsx:97` initializes the account field from username;
  creation sends username/password at lines112–113 and renders Username at line164.
- `crates/gateway-core/src/contracts.rs:15` defines UserInfo without email/name;
  UserCreate at line32 likewise lacks those fields.

## Expected behavior and acceptance criteria

1. Administrator user creation includes required **Name**, **Email** and **Password**
   fields, with clear validation feedback.
2. Store and return name/email as distinct profile fields; user management displays
   them and supports appropriate profile edits.
3. Passwords remain write-only, securely hashed, absent from user list/read responses,
   and changed through the existing protected password/reset flow.
4. Update the database, Rust/TypeScript contracts, UI and relevant tests together;
   preserve stable user IDs, grants, memberships and credential ownership.
5. During implementation planning, specify email uniqueness/normalization, login
   behavior and migration for existing username-only accounts.

This is a product-owner requirement correction to the initial username/password
baseline. Logging it does not revise the approved specification, authorize an
implementation run, or approve the pending MVP completion proposal.


## Product-owner implementation decisions

Email is the sole login identifier; Name is display-only. The owner explicitly
chose no username fallback or backward compatibility because the system is not
live. Use fresh pre-release databases; migration refuses populated older identity
data without deleting it. Implementation is governed by mac-mvp spec2/plan4,
FR-025/AC-013. Final completion approval remains separate.

## Resolution and verification

Commit `fabb614` implements distinct name/email fields throughout storage, generated
contracts, admin create/edit/list, native status and both email-only login screens.
Names never authenticate; canonical emails are unique. Passwords remain write-only.
Profile edits revoke target sessions while preserving stable user ownership.

All 83 Rust workspace tests, 11 real PostgreSQL cases and 44 frontend tests pass,
along with strict TypeScript/lint/format/build/contracts and Clippy. New real-PG
tests cover normalization/validation, duplicate email, stable membership, stale
revision/role/session rejection, concurrent old-email login and safe populated-old
migration refusal. Actual compiled desktop/390px central/native browser journeys
verify create/edit, email login, duplicate feedback and keyboard behavior.

The rebuilt Apple Silicon archive and service image pass extracted-binary
Keychain/all-authentication-mode MCP tests and the fresh deployment-to-Mac-to-STDIO,
restart, backup/fresh restore, wrong/matching-key and redacted-log rehearsal.
Artifact identities and compatibility limits are in [release evidence](../release.md).
