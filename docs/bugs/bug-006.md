## Intended deployment

Deploy the Dhivon control plane to an HTTPS origin reachable by developer clients.
Each local client connects to that origin for Dhivon sign-in, policy and credential
synchronization. Its management listener runs on the developer's machine at
`http://127.0.0.1:{port}`.

When the developer connects an OAuth-protected remote MCP, the native client
supplies `http://127.0.0.1:{port}/oauth/callback` as the authorization request's
`redirect_uri`. After consent, the provider redirects the user's browser to that
local listener with an authorization code and state. The native client validates
the response and exchanges the code with its PKCE verifier over HTTPS. It then
persists the supported credentials through the existing protected flow.

The browser completing authorization must run on the same machine as the local
client. The redirect reaches that machine's loopback listener. Successful MCP
authorization prepares the MCP credential. Dhivon account sign-in and explicit
MCP enablement are separate actions.

## Current evidence

The previous report interpreted the owner's URL comment as public website and
documentation hosting. The clarified request concerns the hosted control plane
and the native OAuth return path.

The implementation already supports this topology.

- `crates/dhivon-mcp-gateway-cli/src/main.rs` accepts the remote `--server` origin,
  binds an IPv4 loopback listener and uses its actual assigned port.
- `src/management.rs` constructs the OAuth callback from that listener's origin.
- `src/oauth_protocol.rs` supplies and verifies the callback URL, S256 PKCE,
  resource and client ID.
- `src/oauth_control.rs` validates and consumes pending consent before code
  exchange and protected credential persistence.
- `deploy/Caddyfile.example` documents HTTPS termination for the control plane.
- Controlled native/OAuth and deployment fixtures passed. A named real provider
  against an actually deployed public HTTPS control plane has yet to be verified.

No callback implementation defect is confirmed by the use of a loopback address.
This follow-up tracks deployment and provider interoperability evidence.

## Expected behavior and acceptance criteria

1. Select and record the actual control-plane HTTPS origin, configure DNS and a
   valid certificate, and deploy the central service behind its HTTPS proxy.
2. Configure the local client with that origin and verify authenticated policy
   synchronization from a developer machine.
3. Configure a supported provider's public native OAuth registration. Use
   `http://127.0.0.1:{port}/oauth/callback` with the local listener's actual port.
   Verify its native loopback port policy or use an explicitly registered fixed
   port through `--port`.
4. Complete consent in the same machine's browser and verify state, issuer where
   required, one-use callback, S256 PKCE and HTTPS token exchange. Token values
   remain outside the callback URL and browser-visible management responses.
5. Verify credential persistence, explicit enablement, a permitted MCP tool call,
   refresh and disconnect with the deployed control plane and named provider.
6. Record the deployed origin, provider/client registration profile, callback port,
   tested versions and cleanup results.

## Standards and implementation handoff

RFC 8252 permits HTTP loopback redirects with an IP literal and requires native
loopback authorization servers to accommodate ephemeral ports. The MCP
authorization specification permits local callbacks and requires PKCE. The
provider's registration and implementation must support the selected native
client profile.

- [RFC 8252, loopback interface redirection](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.3)
- [MCP authorization requirements](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization#communication-security)
- [Current OAuth profile](../oauth.md)
