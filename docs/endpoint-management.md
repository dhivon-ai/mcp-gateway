# Native endpoint management

`mcp-gateway ui --server https://control-plane.example` starts the protected loopback API, native configuration refresh and owned installer lifecycle. Ctrl-C and SIGTERM request graceful shutdown. `ui`, `status` and `logout` accept `--fixture-state-path <existing absolute owner-only directory>` only with `--allow-fixture-http`, for isolated native tests without changing HOME or production state. The real default Keychain uses a separate `com.cadre.mcp-gateway.fixture.*` service derived from that canonical fixture path; normal operation retains its production service. Fixture logout runs through the creating CLI binary so Keychain access control remains enforced. Normal commands use production state. `--no-open`, `--port` and the explicit loopback-only `--allow-fixture-http` option retain their identity semantics. `mcp` still refuses safely until the P4 runtime exists; this group adds no protocol output, shell scripts, coding-agent configuration changes or browser screens.

## Browser contract

The exact Host/Origin, cross-site Fetch metadata rejection, HttpOnly SameSite=Strict cookie and mutation CSRF checks in [endpoint identity](endpoint-identity.md) apply to every route below. `GET /api/context` includes `status.identity.generation`. Generation is ordinary metadata: it supplements local authentication and prevents an old UI action from targeting a newly logged-in account. Never place credentials or local capabilities in a URL, localStorage or sessionStorage.

All new mutations use the JSON envelope `{ "expectedGeneration": "<displayed generation>", "input": <typed input> }`. Reads below require `X-Endpoint-Generation`. Browser logout also requires that header: it checks and clears the expected generation under one state lock and revokes only that old native principal. Logout cancellation is scoped to that generation; process exit cancels all jobs owned by that process. Login is an explicit identity transition, using the existing email/password request.

| Local route | Method / input | Metadata response |
| --- | --- | --- |
| `/api/catalog` | GET | `LocalCatalog`, effective policy, auth requirement, stable selected secret reference, installed and availability metadata |
| `/api/settings/{mcpId}` | PUT `SettingsUpdate` | confirmed `LocalCatalog` |
| `/api/secrets` | GET / POST `SecretWrite` | secret metadata list / `SecretMutationOutcome` |
| `/api/secrets/{secretId}` | PUT `SecretWrite` / DELETE `VersionInput` | `SecretMutationOutcome` |
| `/api/secrets/{secretId}/key` | PUT `SecretRename` | `SecretMutationOutcome` |
| `/api/mcps/{mcpId}/install` | POST `InstallRequest` | 202 `InstallProgress` |
| `/api/installations/{jobId}` | GET | `InstallProgress` |
| `/api/installations/{jobId}/cancel` | POST `input: null` | cancellation requested; poll progress for completion |
| `/api/installations/{jobId}/enable` | POST `SettingsUpdate` with `enabled: true` | confirmed `LocalCatalog`; no installer rerun |

Paths accept bounded identifier segments only. JSON bodies are bounded to 128 KiB so the central 16 KiB secret-value limit also accommodates JSON escaping. Parse failures return fixed errors. Vault values are accepted only as write inputs; responses deserialize strict metadata types. No credential-read/OAuth/endpoint-token endpoint is proxied. Commands, args, environment values and full native snapshots never appear in browser responses or generated local metadata DTOs. The earlier central `ConfigSnapshot` contract remains native; local errors return `LocalApiError.current` as catalog metadata instead of its runtime configuration.

## Confirmed settings and vault writes

Every central mutation and vault read performs a new, complete, authenticated online refresh, even when a valid offline lease remains. The requested generation must match both the subsequently loaded native session and the freshly validated snapshot. Requests pin that exact session token, so concurrent login cannot redirect a pending write to another principal. Revision checks precede dispatch; the central API independently applies revision/version compare-and-set. Conflicts retain the central HTTP status, error code and revision, with fixed diagnostic text and a redacted current catalog when supplied. There is no automatic conflict retry, optimistic toggle or mutation queue.

A successful settings response must describe the requested setting and a newer revision. The native endpoint validates and atomically publishes that complete snapshot through `SnapshotCache` before acknowledging it. A server write followed by local cache/Keychain failure returns failure, never a confirmed enabled response. Recover with complete online synchronization and explicit review; the server may already have applied the write. A late poll cannot regress the committed revision. Snapshot leases retain all [cache rules](endpoint-cache.md), including exact expiry, session deadline, clock uncertainty and retirement barriers.

A confirmed vault mutation returns only metadata. Its follow-up complete refresh sets `synchronized`; if that refresh fails without changing identity, `confirmed: true, synchronized: false` describes the already-completed central write. It does not renew a lease or authorize offline mutation. 401 invalidates the matching generation; a network outage does not invalidate identity. Logout and local cancellation remain available without central connectivity.

## Installation and recovery

Installation is an explicit online action for an assigned active MCP with a centrally configured install command. The MCP must first be centrally disabled. `InstallRequest` includes `expectedRevision`, `enableAfterInstall`, `secretId` and `rerun`. No enablement is implied by starting an installer. Native execution passes program, argument array, environment map and optional cwd directly to Tokio Command, without a shell. Inherited environment is cleared; a system PATH and HOME are provided before explicit configured overrides. Standard input/output/error are null. Fixed progress reports distinguish missing executable/working directory, permission failure and ordinary failure without exposing raw OS diagnostics, command text or process output.

The installer has a sleep-aware native 300-second maximum; tests may reduce this bound. Every 100 ms it reads the latest shared committed cache and checks generation, assigned active definition, disablement, command digest, lease and clock. Cancellation, expiry, known revocation, command change and identity transition stop execution and do not enable the MCP. One owner-only `install.lock` serializes installation across endpoint processes; attempts while occupied fail rather than queue.

`installations.json` is an atomic owner-only, bounded receipt journal, scoped by installation UUID and origin/deployment/user identity. It stores a command digest, job IDs, times and redacted outcomes, never commands, environment values or credentials. Receipts survive logout to describe already-created local side effects, but never authorize access. Only a receipt matching the current command digest marks an installation as installed. At most 256 receipts / 256 KiB are retained. A running receipt without an active owner lock reports interrupted/uncertain outcome. An installer may have made partial changes before failure or termination; this endpoint does not uninstall or roll back external side effects.

Successful local execution durably records `installed_disabled` before any optional central enable request. After owned cleanup, generation, assignment, clock, lease and the native install deadline are checked again before any refresh can authorize automatic enablement. A confirmation fence retains that lease deadline until enable dispatch, so refreshing cannot revive an expired installation. Known local success followed by lost authorization stays installed-disabled with an explanatory receipt. Only the explicit `enableAfterInstall` intent can trigger that request, which must still complete online validation and durable snapshot publication. A subsequent central outage/conflict/rejection leaves an installed-but-unconfirmed-enable result and does not rerun the command. `rerun: false` returns the matching previous receipt; an interrupted or failed attempt also requires an explicit `rerun: true`. The separate `/enable` action retries central settings only. Catalog `enabled` always comes from confirmed central configuration.

## Owned process lifecycle

The reusable macOS `OwnedProcess` helper creates a distinct process group for each structured command. Safe rustix `waitid(EXITED | NOHANG | NOWAIT)` observes exit while preserving the leader zombie/PID. TERM, group KILL before leader reaping, and reaping share one deadline of at most five seconds; a short part of that budget is reserved for reaping. Its Drop guard kills that unreaped owned group on cancellation/aborted futures. It never scans and signals unrelated processes. Descendants that deliberately escape the group or change signal permissions require an external supervisor; abrupt SIGKILL of the endpoint itself cannot run its Drop/graceful handlers.

Apple [waitid implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_exit.c) preserves the child when WNOWAIT is set. The pinned safe nix API exposes waitid only on other targets, so this macOS helper uses rustix 1.1.5 process APIs. Actual testing also found that Darwin [killpg1](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c) excludes zombie members and returns EPERM for a zombie-only group. Cleanup confirms the leader is exited and queries only its reserved group with the safe libproc 0.14.11 API. It accepts EPERM only when every listed member is a confirmed zombie; query errors or live members fail cleanup. The maintained list API uses errno to distinguish zero results, so safe nix Errno::clear precedes the query. EPERM alone never means success.

## Verification boundary

Focused fixture tests cover central outage/refusal/conflicts, strict write-only vault responses, durable settings publication failure, generation interleavings, protected loopback requests and redaction. Actual macOS 27.0.1 arm64 tests execute uniquely owned Python fixture processes with literal shell-looking arguments, explicit env/cwd, successful and failed exits, TERM-ignoring grandchildren, cancellation, Drop/abort and cleanup. Expiry, clock uncertainty, revocation and shortened install limits use deterministic time while executing real Mac children. These are not claims of an actual 300-second wait, machine sleep/reboot, older macOS compatibility or completed browser/P4/P5 runtime behavior.

The initial signal fixture attempted Keychain deletion from its separate parent test binary; macOS access control refused it. The creating CLI logout is now used instead, with fixture-specific services and journals preserved on cleanup failure. Three orphaned entries from that failed approach were recovered only after matching the exact owned creator ACL, common generated account namespace and failed-test interval; exact service/account deletions were verified absent with metadata-only queries. No credential values were inspected or production session selection changed.
