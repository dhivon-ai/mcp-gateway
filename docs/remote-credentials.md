# Native remote credentials

Administrators configure a remote Streamable HTTP MCP with `none`, `bearer`, or `oauth` authentication. For bearer mode, the user creates a key/value secret in their central secret store and selects that key's stable ID while enabling the assigned MCP. The server checks ownership and current revision. Values remain encrypted centrally and write-only in browser APIs; see [the vault contract](vault.md).

The native gateway resolves only assigned, active, centrally enabled MCPs through the authenticated central credential API. It checks the returned secret ID/version against the current encrypted snapshot and sends only the selected upstream token to the exact configured remote URL. Central login tokens are never forwarded to an MCP. Remote redirects are rejected and cannot receive the token. Unauthenticated MCPs send no Authorization header.

Endpoint credential copies are encrypted files in the [single-key endpoint store](endpoint-identity.md#native-state-and-keychain-ownership). The server remains authoritative. A native pull checks identity, assignment, MCP/runtime binding and version before publishing a replacement under fresh local key material. Independent authenticated evidence preserves the token fingerprint, original time anchor and rejection barrier. Corrupt token data cannot be used offline; a successful repair does not rotate the provider key or extend the policy lease.

Every listing and call checks the current protected credential head, its version/binding, and the current policy proof. A new configuration revision requires authenticated credential revalidation. Stable token signatures allow connections to be reused when revalidation confirms the same credential. A new secret version blocks the old connection before discovery can establish a replacement. Metadata-name changes remain separate from token values.

Native credential publication compares the encrypted snapshot's protected receipt. Reading the cache rotates its rollback watermark, which does not itself change the receipt or lease. Credential requests and downloaded tokens never renew configuration freshness. Protected token time anchors likewise remain unchanged when the server returns an identical credential; OAuth access expiry uses both absolute time and sleep-aware elapsed time.

During a control-plane outage, an existing protected credential may be used only while its binding, token, session, and one-hour policy lease remain valid. If the server refuses a credential request with HTTP 403, that MCP stays blocked across an offline restart. This also applies on the first fetch: a successful response from a request already in flight cannot undo the refusal. A fresh authorized response can restore access. Other eligible MCPs remain usable. A missing key, a foreign key, or a version mismatch also blocks fallback. Remote rejection is recorded for the exact credential signature; a late response cannot reject a newer token or another login. A changed key/value version or an explicitly reauthorized OAuth record can recover. Credential changes, installation, and new OAuth connections remain online-only.

The default gateway reports fixed categories such as `auth_required`, `auth_rejected`, and `token_expired`. Tool-policy denial still rejects direct calls before the upstream. A failed authenticated MCP leaves unrelated healthy tools usable. [OAuth discovery/PKCE/callback and coordinated refresh](oauth.md) use the separate native management flow; the STDIO entry never starts interactive consent.

Verification includes protected fixture calls with central/upstream header witnesses, owned-key replacement, foreign-key response rejection, upstream HTTP 401 isolation, valid cached bearer use at 3,599 seconds and denial at 3,600, and failure recovery without token lifetime extension. Actual macOS 27.0.1 arm64 CLI tests resolve a bearer token into the protected endpoint store and invoke a protected SDK HTTP MCP through the single agent-facing STDIO entry; local files contain no plaintext token values, and creating-CLI logout clears the scoped credentials. Production TLS and actual-provider interoperability follow the declared release/profile evidence rather than the loopback fixture exception.

A login generation tracks at most 128 credential-bearing MCP identities, including formerly assigned MCPs. Replacing an existing credential does not consume another identity slot. A new MCP beyond that bound reports local credential capacity without changing existing heads, corrupting the shared identity, or blocking status/sync/logout. Log out and sign in again while online to clear retired credentials and start a fresh generation. Metadata writes enforce the same schema, ownership, pointer and count invariants as reads before replacing the durable file.
